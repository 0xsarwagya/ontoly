## Why

The graph is the artifact every downstream tool consumes. Build it once, then
query, validate, export, or expose it through MCP.

## Build

Run against any language repository — Ontoly detects `.ts`, `.js`, `.py`,
and `.go` sources automatically:

```sh
ontoly build ./my-typescript-app
ontoly build ./my-django-service
ontoly build ./my-go-api
```

For a self-contained example:

```sh
ontoly build examples/basic
```

The compiler:

1. discovers package manifests (`package.json`, `pyproject.toml`, `go.mod`) and language source files
2. parses source with the appropriate language frontend
3. extracts symbols
4. extracts relationships
5. runs framework analyzers (29 across three languages — see the [Framework Matrix](../framework-matrix.md))
6. builds indexes
7. writes graph artifacts

Artifacts are written to `ontoly-output/` by default:

```text
SoftwareGraph.json
manifest.json
coverage.json
quality.json
semantic-model.json
reports/
nodes/
relationships/
communities/
html/
```

For the compact cache-style artifact directory, pass `--output .ontoly`:

```sh
ontoly build examples/basic --output .ontoly
```

That writes:

```text
SoftwareGraph.json
graph.json
cache.json
indexes.json
diagnostics.json
metadata.json
statistics.json
```

Identical input should produce identical graph IDs and deterministic graph
hashes. The generated timestamp is intentionally fixed inside the graph
metadata so the graph hash is not invalidated by build time.

## Inspect

```sh
ontoly inspect UserService --root examples/basic
ontoly search UserService --root examples/basic
ontoly impact UserService --root examples/basic
ontoly coverage examples/basic
```

If something feels off:

```sh
ontoly doctor .
```
